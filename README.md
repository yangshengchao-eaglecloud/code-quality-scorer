# code-quality-scorer

给任意软件项目打一个 **0-100** 的代码质量分。

只评「代码是怎么组织的」——分层、封装、数据流、模块边界、演进健康。不评业务功能对错，不评算法优劣，不评性能。规则与编程语言无关：任何语言的项目用同一把尺子。

> 这是一个 AI 编码助手技能包（skill）。把本目录放进助手的 skills 目录即可使用，见[使用方法](#使用方法)。

---

## 它解决什么问题

「这个项目代码质量怎么样」这个问题，日常得到的回答通常是印象式的：有人说分层乱，有人说还行，没有共同标尺，也没法量化，更没法在两个项目之间做对比。

这个评分器把「代码组织得好不好」拆成 **10 个可核查的结构维度**，给一个 0-100 的总分、一份按严重度排序的问题清单，以及每条问题的修复方向。同一个尺子量所有项目，因此可以横向对比，也可以看同一个项目整改前后的变化。

它同时用来识别一类特定问题：**单看每个模块都说得过去、整体看不像人写的代码**。这类代码的病根在整体层（同类问题到处是不同解法、为不会发生的情况写防御、发明不存在的需求），逐模块评审永远发现不了，只有跨模块拉通评才看得见。

## 评什么、不评什么

| 评 | 不评 |
|---|---|
| 分层是否各归其位 | 业务功能对不对 |
| 封装是否彻底、暴露面是否最小 | 算法优劣 |
| 数据流是否显式可追踪 | 性能高低 |
| 调用方是否需要懂内部规则才能用 | bug 数量（评的是组织形态，不是缺陷数） |
| 模块能否抽象为「输入 → 处理 → 输出」 | 测试用例（根本不打开，不读不评不当证据） |
| 策略是否与代码分离、执行路径是否可读 | 项目自带的说明文档与宣传材料（不看，只认源码与配置） |
| 演进是否健康（有无收敛、有无重复决策） | 代码格式与缩进风格 |

两条容易被误传的规则，单独说明：

- **测试用例不是输入。** 可测性只从代码设计面看：有没有接缝、有没有注入点、依赖是否纠缠、全局状态有多少。模块能不能被测是设计出来的属性，与测试写没写无关。
- **命名与文档的承诺不算数，兑现才算。** 组件叫 `config_manager` / `models` / `app_main`，只说明意图不说明事实——配置中心是否真有统一入口与快照、模型层是否只放数据，逐项按代码实况验证。凡是「架构活在命名里」的，如实报告。

## 评分依据

### 四大基本要素

一切维度的根基是面向对象四大要素，维度和质量属性只是这些要素在工程上的投影：

| 要素 | 是什么 | 失守的典型形态 |
|---|---|---|
| **封装** | 数据与操作数据的行为绑在一起，对外只暴露必要接口 | 数据和行为分家，外部类逐字段读写别人的数据结构；调用方必须懂内部规则才能选对方法 |
| **抽象** | 用「做什么」代替「怎么做」，分层即分级抽象 | 实现细节漏进调用点，调用方代码里复述被调方的内部规则 |
| **继承** | 「是一个」关系，白盒复用、最强耦合，慎用 | 为拿到实现而继承；子类不能无条件替换父类 |
| **多态** | 同一语义接口多种实现，新增情况不改调用方 | 调用点散布 switch/if 复述类型分派，加一种情况要改所有调用点 |

封装是其余三要素的载体：没有封装，继承继承到的是一堆散乱字段，多态没有稳定接口可替换，抽象没有落点。

### 从要素到维度

四大要素是材料，**七个设计原则**（单一职责、开闭、里氏替换、依赖倒置、接口隔离、合成复用、迪米特法则）是运用材料的工程法则；**内聚与耦合两把标尺**（各七级）判断模块独立性，理想模块是「功能内聚 + 数据耦合」；**23 种设计模式**是常见场景的标准解法，但评分时双向判据——该用而不用的扣分，只有一种实现却套抽象工厂的同样扣分，模式是缺失时的解药，不是默认配料。

这些收敛为 10 个结构维度：

| # | 维度 | 报告强调度 | 一句话规则 |
|---|---|---|---|
| 1 | 层次分明 | 15 | 三层各归其位：工具层无业务、共用数据模型集中、业务实现收敛在业务层 |
| 2 | 封装彻底、最小暴露面 | **20** | 字段封装为语义函数对外服务；暴露面不大于必要 |
| 3 | 调用方知识边界 | **15** | 调用方不许被要求懂内部规则才能选对调用 |
| 4 | 数据流清晰 | 10 | 数据显式传递、来去可追踪，不走隐式全局通道 |
| 5 | 业务流清晰 | 7 | 业务步骤序列可读可追溯，有明确编排点，异常路径显式 |
| 6 | 模块边界 | 10 | 每个模块能抽象为输入→处理→输出 |
| 7 | 策略与代码分离 | 5 | 可变语义（阈值/开关/等级规则）进配置，代码零策略 |
| 8 | 校验放对位置 | 3 | 必填靠类型声明、版本靠版本号协商、格式约束靠结构定义 |
| 9 | 演进健康 | 5 | 局部补丁不许替代体系级能力；同一决策不许多份表达 |
| 10 | 对象组装 | 10 | 业务对象在程序入口统一创建传递，不许自立全局单例 |

其中 7、8、9 属**内务维度**（配置、校验、演进），合计拉低总分不超过 10 分——小毛病全部进问题清单，但不许把分数拉穿；结构侧维度决定分数水位。

### 质量属性面板

总分之外，按映射把结构维度分投影为 8 个教科书质量属性分（每个属性 = 其映射维度得分的平均），用来定位「这个项目差在哪个质量目标上」：

| 质量属性 | 支撑它的结构维度 |
|---|---|
| 易读 | 数据流清晰、业务流清晰 |
| 易维护 | 层次分明、封装、知识边界、演进健康 |
| 易扩展 | 封装、知识边界、模块边界可测、策略分离 |
| 简单 | 校验放对位置、演进健康（无过度设计） |
| 灵活 | 策略与代码分离、对象组装 |
| 易测试 | 数据流清晰、模块边界可测、对象组装 |
| 易移植 | 层次分明（通用层与业务隔离）、策略与代码分离 |
| 安全边界 | 封装（最小暴露面）、校验放对位置（边界处拦截不可信输入） |

## 参考源

本评分器的两条重要参考源（均为公开项目）：

| 参考源 | 它是什么 | 与本评分器的关系 |
|---|---|---|
| [brooks-lint](https://github.com/hyhmrright/brooks-lint) | 植根于十二本经典工程著作的 AI 代码审查：衰退风险诊断、结论带书目出处、严重度分级 | 同一条主张的两条实现路径——**诊断必须可溯源**。它的结论落回经典著作，本评分器的结论落回四大要素与十个维度；它的「症状 → 根源 → 后果 → 对策」与本评分器「每条发现四段齐」是同一件事：不给出一条能指到出处的结论，就不算一条发现 |
| [linus-torvalds-skill](https://github.com/Mte90/linus-torvalds-skill) | 从 31,397 封 Linux 内核邮件列表邮件里提取 38,293 条真实评审，蒸馏出的与语言无关的代码评审方法论 | 「好品味」与「简单与灵活」两节的思想同源——特判能不能被更好的数据结构整个消掉、用设计买兼容而不是用代码量买兼容；评审只认代码本身、命名与文档的承诺不算数 |

两者与本评分器共享同一条底线：**评价的输入只有代码与配置**，命名是承诺不是事实，兑现才算。

## 评分标准

### 分数段

| 分数段 | 含义 |
|---|---|
| 90-100 | 教科书级，可作范本 |
| **80-89** | **规范**——结构清晰、分层方向正确、缺陷零星可修 |
| 60-79 | 结构成立，存在系统性短板 |
| <60 | 结构性塌方 |

### 问题级别

| 级别 | 含义 | 对应范围 |
|---|---|---|
| P0 | 灾难级：架构整体不成立、根本无法安全使用 | 塌方级 |
| P1 | 严重：结构性缺陷，或同类问题成片已是默认写法 | 系统性 |
| P2 | 中等：多个模块 / 多个调用点存在同一模式 | 普遍 |
| P3 | 轻微：个别点状问题、改进建议 | 局部 |

分数与判级必须一致：总分落在塌方段或命中封顶条款时，把分数压到那里的主问题必须标 P0；反过来，对结构清晰、方向正确的代码打出 P0，先回头查是不是把行业惯例或点状瑕疵上纲了。

### 封顶规则

结构性缺陷直接压总分上限，与维度分取更低者：

| 形态 | 总分上限 |
|---|---|
| 完全摆不出三层（数据、行为、工具混装一锅） | 30 |
| 共用数据模型无集中定义点（散布各处） | 40 |
| 详细业务层无统一形态（散件类遍地） | 50 |

### 三条评分纪律

- **结构锚定**：分数评的是代码组织形态，不是 bug 数量。模块边界清晰、封装收口到位的代码 85 分起步；点状缺陷（某处注入面、某行假返回、个别越界）合计拉低总分不超过 8 分——必须进清单，但不决定水位。分数能压到 50 以下的唯一通道是结构重扣条款：知识泄漏成默认写法、数据模型散布各层、业务渗入工具层、跨服务共享上下文无收口、假分层、组装失控成群，每类从基线扣 12-18 分。
- **总分不是加权平均**：总分由整体判断给出、落在段位内。维度表是证据的组织形式（解释为什么是这个分、差在哪、好在哪），不是算术输入。禁止机械加权算总分。
- **一次违规一次计罪**：同一问题只在主维度扣分，其他维度引用作佐证不重复扣。每个扣分落到 `文件:行号` + 一句定性——无证据不扣分，有证据必扣分。

### 分数即客观结论

评分器给出的分数就是最终分数，一份报告里只有一个分数。分数只由代码实况决定——证据、维度判定、封顶与限幅规则说了算；评审者身份、项目状态、整改进度、团队约束、交付压力都不进入分数。同一份代码换谁来评、什么时候评，分数应当落在同一位；分数不稳就是判定没落到证据上，回头补证据，不是调分。已作出的判定不得为迎合任何外部预期而改分或改证据——分数与证据不符时，改证据不改分数。

### 只读保证

评分任务绝不修改、删除、移动被评项目的任何文件。发现问题写进报告，处置权在项目所有者。

## 使用方法

```bash
# 1. 放到 skills 目录（目录名即技能名）
git clone https://github.com/yangshengchao-eaglecloud/code-quality-scorer.git \
  ~/skills/code-quality-scorer
```

```text
# 2. 在 AI 编码助手里直接提问

给 /path/to/xxx-service 打个代码质量分

评一下 xxx-service 的代码质量，和 xxx-gateway 对比着看

只看 xxx-service 的封装与模块边界，逐个模块给结论

xxx-service 这次重构之后，代码组织比上个月好还是差了
```

输出是一份固定六段的报告：总分与一句话定位 → 好的方面 → 质量属性面板 → 结构维度明细 → 封顶判定 → 问题清单（P0→P3，每条含症状、出处、后果与修复方向）。

### 渲染后的效果

[examples/report-sample.html](examples/report-sample.html) 是完整输出的 HTML 渲染版，含两个项目的对比报告，自上而下为：

1. **汇总表**——每个对象的分数与段位
2. **分数分布**——条形对比，一眼看出谁高谁低
3. **规则要点**——结构主维度权重、限幅与从轻条款（读取分数的口径）
4. **逐项目一节完整报告**——总分与定位 → 好的方面 → 质量属性面板 / 结构维度明细（双栏并排，附封顶判定）→ 问题清单（P0–P3 彩色卡片，每条含症状 / 出处 / 后果 / 修复四段）

纯静态单文件，无外部依赖，下载后用浏览器直接打开即可（GitHub 上点击 HTML 文件默认显示源码，也可启用 GitHub Pages 后在线查看）。

## 仓库结构

```
code-quality-scorer/
├── README.md             # 本文件
├── SKILL.md              # 主文件：四大要素、七大原则、内聚耦合标尺、10 维度细则、报告格式、评分纪律
├── design-patterns.md    # 23 种设计模式详解：每种模式的意图、正当场景、误用信号、维度联动
└── examples/
    └── report-sample.html  # 示例报告（HTML 渲染版，两个项目对比，已脱敏）
```

两个文档的分工：`SKILL.md` 是评分主体，规定了怎么评、怎么报；`design-patterns.md` 是它的判据附录——评分涉及「该不该用某个模式」时，必须先读它再裁，不许凭印象。
